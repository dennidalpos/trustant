# Contributing

Thanks for your interest in contributing to Trustant.

## A Contributor Agreement is required

**We cannot accept a pull request until a signed Contributor License Agreement
(CLA) is on file for its author.** This applies to every contribution of any
size, and to every repository in the Trustant project, including the
vendored `oplugins-truinst/`, `acp/`, `oplugins/`, `skills/` and `mcp/` directories.

Trustant is released under the GNU Affero General Public License, version 3 or
later (see [LICENSE](LICENSE)). Nuvolaris Inc also offers the software under
separate commercial terms. The CLA is what allows us to keep doing both: it
grants Nuvolaris Inc the rights needed to distribute your contribution under
the AGPL *and* under those commercial terms, while you keep the copyright in
the code you wrote.

If you are contributing on behalf of your employer, you need a Corporate CLA
signed by someone authorised to bind that company.

To request an agreement, contact **info@nuvolaris.io** before opening a pull
request. A PR opened without a CLA on file will be left unmerged until one is
signed — please do not spend time on a large change before sorting this out.

## License headers

Every source file carries an AGPL header, enforced by
[license-eye](https://github.com/apache/skywalking-eyes) using the
`.licenserc.yaml` in each repository. Before opening a pull request:

```bash
license-eye header check   # report files missing the header
license-eye header fix     # add it to any file that lacks one
```

Run it from the directory whose files you changed. license-eye discovers files
with `git ls-files`. The Trustant-owned `oplugins-truinst/` directory carries its
own `.licenserc.yaml`; run the check from inside it when you change its files.

The vendored `oplugins/`, `skills/` and `mcp/` directories are upstream Apache-2.0 projects with their
own LICENSE and NOTICE files. Do not add AGPL headers there.

## Third-party licenses

`DEPS`, `LICENSE` and `NOTICE` are generated by `./deps.sh` (see
[spec/20-legal.md](spec/20-legal.md)). When you add, remove or upgrade a
dependency — a Go module, an npm package, a pinned Python package, a
downloaded binary, an ops prerequisite or a package in the image — update
`legal/deps.manual.txt` if the component is not read automatically, rerun
`./deps.sh` and commit the three regenerated files, and update [CREDITS.md](CREDITS.md) if a main component changed.

## Before you open a pull request

- `npm run lint` passes.
- `go test ./...` passes.
- `./deps.sh` was rerun if dependencies changed.
- Specs under [spec/](spec/) are updated when behaviour changes — the spec is
  the source of truth, and is iterated on before the code.
- The change is scoped to one issue.

## Lint

From the repository root, run `npm ci` to install the pinned Biome package,
then run `npm run lint`. Use the Go version in `go.mod`, Python 3.11 or later
for TOML validation, and PowerShell 7. Install the other development tools
on your PATH using the versions in [DEPS](DEPS).

- Install Ruff with `uv tool install ruff==0.14.14`.
- Install [ShellCheck 0.11.0](https://github.com/koalaman/shellcheck/releases/tag/v0.11.0)
  and [Hadolint 2.15.1](https://github.com/hadolint/hadolint/releases/tag/v2.15.1)
  from their release pages or your package manager.
- In PowerShell, run `Install-PSResource -Name PSScriptAnalyzer -Version 1.25.0 -Repository PSGallery -Scope CurrentUser`.

The command runs Go vet for Linux, Biome for JavaScript, TypeScript, HTML
(including embedded scripts and styles), CSS, JSON and YAML, Ruff for
Python, ShellCheck for shell scripts, Hadolint for Dockerfiles,
PSScriptAnalyzer for PowerShell, and syntax validation for TOML. It covers
Trustant, the vendored TruACP and Pi ACP sources, React MCP, and tests.
Submodules keep their own tooling. Generated bundles and third-party
browser assets are excluded. Higher-severity diagnostics are the gate
for ShellCheck, Hadolint and PSScriptAnalyzer.

## Go vulnerability check

Run this separately from lint, from the repository root in Ubuntu. Use the
Go toolchain declared in `go.mod` for both the scanner build and package loading.
The scan needs network access to fetch the scanner and the Go vulnerability
database. The embedded `_build.txt` must exist before scanning (`run.sh` creates
it in development).

```bash
(
  go_root="$(go env GOROOT)"
  export GOROOT="$go_root" PATH="$go_root/bin:$PATH" GOTOOLCHAIN=local
  go version
  go install golang.org/x/vuln/cmd/govulncheck@v1.10.0
  scanner_bin="$(go env GOBIN)"
  scanner_bin="${scanner_bin:-$(go env GOPATH)/bin}"
  "$scanner_bin/govulncheck" -show=version ./...
)
```

Run `go env GOROOT` from the repository root so the Go command resolves the
project toolchain. Putting that toolchain on `PATH` also makes it available to
the scanner when it loads the packages. This procedure was verified with
Go 1.27.4 and govulncheck v1.10.0.

Findings in toolchain or module code reachable from Trustant are fixed or
tracked as tasks; do not bump unrelated dependencies to silence a report.

Lint does not build images, start the application, or rewrite sources.
The Go step supplies temporary embed metadata outside the checkout when
`_build.txt` is missing. Run `npm run lint:web -- web` to check just the
main UI files.
