Verificato su HEAD `482b764` rispetto a `upstream/main` (`630f83c`, v1.0.3, https://github.com/trustant/trustant) e rispetto ai repository remoti dei componenti (clonati con `--no-checkout` in una directory temporanea; i loro blob non sono stati scaricati).

## 4. Non conformità e rischi

### 4.1 Apache-2.0 §4(b): avvisi di modifica mancanti (media gravità)
La sezione 4(b) richiede che i file modificati riportino avvisi ben visibili. Dei 11 file modificati in `oplugins/` e `mcp/`:

- con avviso: `oplugins/debug/runtime/invoke.py`, `oplugins/prereq.yml`;
- **senza avviso** (9): `oplugins/admin/opsfile.yml`, `admin/docopts.md`, `ide/deploy/package.json`, `setup/kubernetes/DEBUG.txt`, `mcp/tests/invoke.test.ts` (commento solo funzionale), `mcp/package.json`, `mcp/requirements.txt`, più i lockfile `oplugins/ide/deploy/bun.lock` e `mcp/package-lock.json` (9 file senza avviso in totale).

I file JSON/lock/requirements non ammettono facilmente commenti. Soluzione pratica: elenco dei file modificati in `NOTICE` o in un file `MODIFICATIONS`/`TRUSTANT-CHANGES.md` nella directory, oltre a `legal/VENDORED.md` (che oggi fa già da registro, ma non è dentro i NOTICE originali, che vanno lasciati intatti). I commenti vanno aggiunti nei file che li supportano (`opsfile.yml`, `docopts.md`, `invoke.test.ts`, `DEBUG.txt`).

### 4.2 Contraddizione sulla licenza di `skills` (bassa gravità, documentale)
`legal/REVIEW.md` dice di aver "corretto il precedente Apache-2.0 in AGPL-3.0-or-later" per `skills`, mentre `LICENSE`, `COMPONENTS.json`, `deps.manual.txt` e `CREDITS.md` dicono Apache-2.0. Il testo LICENSE del repo `trustable-ai/skills` è Apache-2.0 (commit `4c89a8f`). Ha ragione il registro; la tabella in `REVIEW.md` (e la riga "Trustant, ACP, installer plugin and skills (AGPL)") è obsoleta.

### 4.3 Storia: commit originali non raggiungibili (media gravità)
`acp/UPSTREAM.md` e AGENTS.md prescrivono di tenere raggiungibili i commit submodule originali. Per `acp` e `pi-acp` è vero (genitori del merge `b06dc8d`). Per `oplugins` (`27b281e`), `skills` (`56d349b`), `mcp` (`baf1400`) **no**: `c41c63c` è un commit normale e `git cat-file` locale non trova nessuno dei tre. Sono ancora presenti sui remoti (verificato). Il rischio è che un repository di terzi venga cancellato o riscritto. Mitigazione: vedi 5.4.

### 4.4 Copyright e CLA (da confermare con il titolare)
- Le intestazioni AGPL aggiunte portano "Copyright 2025-2026 Nuvolaris Inc", ma 127 commit del fork sono di Danny Perondi e altri di Claude (co-autore). Non è un'infrazione licenziale, ma una dichiarazione di titolarità. `CONTRIBUTING.md` richiede un CLA a favore di Nuvolaris Inc.: verificare se il fork debba mantenere questa titolarità o usare la propria.
- `acp/pi-acp` è documentato come fork `trustable-ai/pi-acp` in `COMPONENTS.json` ma `trustant/pi-acp` in UPSTREAM.md: uniformare.

### 4.5 Altri punti
- `oplugins/util/upload/.env.test` è stato rimosso nel fork. Va bene (nessuna perdita di licenza), ma conferma che l'originale non conteneva segreti reali.
- L'inventario `legal/` dichiara un'ultima revisione del 2026-11-19 con aggiornamenti; non è un parere di legittimità sull'immagine pubblicata (lo dice il documento stesso).

### 5.1 Compromessi
- **Pro**: i LICENSE/NOTICE originali tornano a essere quelli del repo sorgente, intoccati; un solo posto da cui seguire gli avvisi di modifica (il repo del componente); la storia dei componenti resta con i loro autori.
- **Contro**: ogni modifica locale ai componenti richiede push su un repo di terzi (AGENTS.md lo vieta: "Never push to third-party repositories") o su un fork. Il titolare ha scelto di vendorizzare proprio per questo (`b06dc8d`, `c41c63c`). Le modifiche locali (§2.2) andrebbero spostate su fork.
- `trustant/*` appartiene all'organizzazione upstream (non al titolare del fork). `trustable-ai/*` anche. Per mantenere le modifiche serve **un fork per ogni repo** (es. `dennidalpos/…`) e un `.gitmodules` che punti ai fork.
- Compromesso intermedio, **raccomandato se si vuole conservare la vendorizzazione**: lasciare le directory ma aggiungere gli avvisi mancanti (4.1) e rendere raggiungibili i commit originali (5.4).

### 5.2 Procedura per ripristinare un gitlink (esempio `skills`, nessuna modifica locale)
Eseguire dalla radice, su un branch dedicato, solo dopo autorizzazione esplicita:

```bash
git checkout -b restore-gitlinks
git rm -r skills
git submodule add -b main https://github.com/trustable-ai/skills skills
git -C skills checkout 56d349b6174e53707723ed839c252995122dc46d
git add skills .gitmodules
```

Lo stesso schema vale per gli altri, con il commit della tabella. Per `mcp` e `oplugins` con modifiche locali, prima crea un fork, applica il delta e poi punta il gitlink al commit del fork:

```bash
# patch delle modifiche locali rispetto alla baseline (dal registro VENDORED.md)
git diff --binary baf14007f9106cfd63b1396fd5d374f7dd9b7537^{tree} HEAD:mcp > mcp-since-baseline.patch
```

Per `acp` e `acp/pi-acp` la procedura e le patch sono già descritte in `acp/UPSTREAM.md` (`git diff --binary 9786f796380a^{tree} HEAD:acp`). Nota: quel comando usa un hash che non è un tree locale in tutti i casi; verificare con `git rev-parse 9786f796380a^{tree}` prima di usarlo.

### 5.3 Dopo il ripristino
Aggiornare: `.gitmodules`, `.licenserc.yaml` (rimuovere le esclusioni), `legal/COMPONENTS.json` e `legal/deps.manual.txt` (da `vendored` a `submodule`), `CREDITS.md`, `AGENTS.md`, `start.sh`/`setup.sh`/`image/image.sh` (reinizializzare i submodule), spec; rieseguire `./deps.sh` e `python legal/vendored_changes.py`. Non riscrivere la storia.

### 5.4 Mettere in sicurezza la storia (fattibile subito, a basso rischio)
Rendere raggiungibili i commit originali senza cambiare la struttura:

1. Fork dei quattro repo (`openserverless-task`, `skills`, `openserverless-mcp`, `trustant-acp`) sotto l'account del titolare: un fork conserva i commit anche se l'origine sparisce.
2. In alternativa o in aggiunta, fetch locale e tag di ancoraggio:
   ```bash
   git fetch https://github.com/trustable-ai/openserverless-task 27b281eb7615c9094f1c6edab10a2b4fe2fd621c
   git tag vendor/oplugins-baseline FETCH_HEAD
   ```
   (ripetere per `skills` `56d349b…` e `mcp` `baf1400…`). I tag locali non protetti vanno poi pushati solo con autorizzazione.
